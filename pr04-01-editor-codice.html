Git registra modifiche, non “salva nel cloud”

L'integrazione grafica mostra file modificati, differenze, branch e conflitti. Le operazioni restano quelle di Git.

In pratica: modifica → controlla il diff → stage → commit → eventualmente push.

Diff

Confronta prima e dopo, riga per riga.

Commit

Registra un insieme coerente di modifiche locali.

Branch

Permette di lavorare su una linea separata.

Remote

Sincronizza con GitHub o un altro server quando fai pull o push.

Git: ciò che non deve entrare nel repository

Non tutto quello che sta nella cartella va versionato. Il file .gitignore elenca ciò che Git deve ignorare, e ignorare le cose giuste è una questione di sicurezza, non di ordine.

Le password, mai

Chiavi, token e password non entrano nel codice: stanno in un file di configurazione locale (per esempio .env), che il .gitignore esclude. Una chiave finita in un repository pubblico va considerata compromessa — anche se la cancelli dopo, resta nella storia.

I file generati, mai

Le dipendenze scaricate e i file prodotti dalla compilazione si rigenerano da soli. Versionarli gonfia il progetto e produce conflitti a ogni aggiornamento.

Le impostazioni personali

Il tuo tema e la tua dimensione del carattere non riguardano gli altri. Le impostazioni del progetto, invece, sì — e quelle si condividono apposta.

⚠️ Attenzione

Il .gitignore va scritto prima del primo commit. Se un file è già stato versionato, aggiungerlo al .gitignore non lo rimuove dalla storia: continua a essere lì, per chiunque scarichi il progetto.

Git: il conflitto non è un guasto

Quando due persone modificano le stesse righe, Git non sceglie per te: si ferma e ti mostra le due versioni. Il conflitto è la prova che il sistema sta funzionando — ti sta impedendo di cancellare in silenzio il lavoro di qualcun altro.

Cosa vedi

L'editor mostra le due versioni affiancate: la tua e quella arrivata. Scegli l'una, l'altra, o scrivi la combinazione corretta — che spesso è la risposta giusta.

Come si evita

I conflitti nascono dai rami lasciati indietro per giorni. Aggiornare spesso il proprio ramo li rende piccoli e leggibili, invece che enormi e spaventosi.

<<<<<<< il tuo lavoro sconto = 0.10 ======= sconto = 0.15 >>>>>>> il lavoro arrivato // Non è un errore da cancellare: // è una domanda a cui rispondere.

Git: leggere una diff prima di unire

La diff è il confronto tra prima e dopo: righe tolte in rosso, aggiunte in verde. Saperla leggere è la competenza che trasforma il versionamento da archivio a strumento di controllo.

Rileggi te stesso

Prima di consegnare, guarda la tua diff. È lì che trovi il file di prova dimenticato, la password lasciata per errore, la riga di debug che non doveva restare.

Revisione tra pari

Su un progetto condiviso, il codice si legge prima di unirlo. Non è un esame: è il modo più economico di trovare un errore, molto prima che lo trovi un utente.

Commit piccoli

Una diff di trenta righe si legge davvero; una di tremila si approva senza guardarla. La dimensione del commit decide se la revisione sarà reale o finta.

Formatter, linter e test: tre controlli diversi

🧹

Formatter

Uniforma spazi, rientri e stile. Riduce discussioni estetiche, ma non verifica la logica.

🔎

Linter / analisi

Segnala pattern rischiosi, errori probabili e violazioni delle regole configurate.

✓

Test

Esegue casi controllati e confronta risultato ottenuto e risultato atteso.

Automazione utile

Salvataggio automatico, format on save e test rapidi sono comodi soltanto se il team condivide configurazioni e regole.
